## Background & Goal
The first transcript feature (see `TRANSCRIPT_LOGGING_FEATURE_PLAN.md`) captures system instructions and input prompts dispatched to participant agents via the transcript logging pipeline (`TranscriptLogger`, `run_with_transcript_logging`). The new requirement is to **also persist each agent's returned prompt/output** for every captured interaction, while preserving existing configurability and performance trade-offs.

Key alignment points with the original plan:
- Reuse the established wrapper pattern (`run_with_transcript_logging`) and dependency injection flow.
- Maintain optional, configuration-driven behavior with conservative defaults.
- Keep transcript logging resilient (never block experiment flow on logging failures).
- Extend rather than break existing JSON schema consumers.

## Functional Requirements
1. **Output Capture**: Record the textual response generated by the participant agent for every interaction already captured (Phase 1, Phase 2, voting, memory updates when enabled).
2. **Configurability**: Introduce a toggle (default `true`) to control inclusion of agent outputs, analogous to `include_input_prompts`.
3. **Schema Compatibility**: Extend transcript JSON in a backward compatible manner; existing consumers must continue to parse prior fields.
4. **Metadata Consistency**: Ensure call numbering, timestamps, and interaction typing remain unchanged.
5. **Failure Isolation**: Logging failures (e.g., serialization, file write) must still be non-fatal.

## Non-Functional Requirements
- **Security**: Agent responses may contain sensitive or unexpected content. Document this clearly but default to `True` for consistency with `include_input_prompts` (both capture primary conversational data).
- **Maintainability**: Encapsulate new logic within transcript utilities and unit-tested helpers.
- **Testing**: Expand unit test coverage with minimal integration validation.

## Current Architecture Snapshot
- `TranscriptLogger.record_interaction` persists `TranscriptInteraction` models with `instructions` and `input_prompt`.
- `run_with_transcript_logging` wraps `Runner.run`, capturing instructions pre-call and logging metadata post-call.
- Configurable flags (`include_instructions`, `include_input_prompts`, `include_memory_updates`) govern payload contents.
- JSON schema is hierarchical: experiment metadata → per-agent transcripts → sequential call objects.

## Proposed Solution Overview
1. **Config Extension**: Add `include_agent_responses: bool = True` flag to `TranscriptLoggingConfig`.
2. **Data Model Update**: Extend `TranscriptInteraction` model with `output_response: Optional[str]`.
3. **Wrapper Enhancement**: Capture `str(result.final_output)` after `Runner.run` and conditionally pass to `record_interaction`.
4. **Testing**: 3 focused unit tests + 1 lightweight integration test.
5. **Documentation**: Update config examples with warnings about sensitive data exposure.

**Note**: No schema versioning required—optional fields are inherently backward compatible.

#### Task 1.2: Data Model Extension (10 min)
**File**: `utils/logging/transcript_logger.py`
- Add `output_response: Optional[str] = None` to `TranscriptInteraction` model

- Existing serialization (`model_dump`) automatically handles optional fields

#### Task 1.3: Logger Method Update (10 min)
**File**: `utils/logging/transcript_logger.py`
- Add `output_response: Optional[str] = None` parameter to `record_interaction()`
- Pass through to `TranscriptInteraction` constructor
- Backward compatible (optional parameter with default)

#### Task 1.4: Wrapper Integration (25 min)
**File**: `utils/logging/transcript_logger.py` → `run_with_transcript_logging()`
```python
# After capturing `result = await Runner.run(...)`
if transcript_logger and transcript_logger.is_enabled():
    agent_response = None
    if (
        transcript_logger.config.include_agent_responses
        and result.final_output is not None
    ):
        agent_response = str(result.final_output)

    transcript_logger.record_interaction(
        # ... existing parameters ...
        output_response=agent_response
    )
```

**Notes**:
- Keep the existing `record_interaction` call inside the enabled guard to avoid dereferencing `None` loggers.
- Preserve `None` outputs (e.g., exceptions) by leaving `output_response` unset instead of serializing the literal string "None".

## Risks & Mitigations
- **Sensitive Data Exposure**: Agent responses may contain unexpected sensitive content
  - **Mitigation**: Clear documentation warnings; recommend secure storage
  - **Note**: Default `True` for consistency with `include_input_prompts` (both are primary conversational data)
- **Large Payload Growth**: Response capture increases transcript JSON size
  - **Mitigation**: Document expected growth; consider adding truncation in future if problematic
  - **Note**: Output length similar to input prompt length; not a breaking concern
- **Backward Compatibility**: External tools parsing transcripts
  - **Mitigation**: Optional fields are inherently backward compatible (consumers ignore unknown fields)
  - **Note**: No schema versioning needed

## Out of Scope / Future Enhancements
- Response truncation/length limits (capture full output initially; add only if file size becomes problematic)
- Partial redaction or filtering of sensitive content
- Streaming or incremental transcript persistence during long runs
- UI tooling for diffing or replaying transcripts
