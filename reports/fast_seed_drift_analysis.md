# fast.yaml Determinism Analysis

## Overview
Running `fast.yaml` twice with `seed: 42` and all agent temperatures forced to zero (`config/fast.yaml:3-20`) still produced divergent transcripts and metadata. This report traces what is deterministic today, pinpoints the remaining sources of nondeterminism, and outlines mitigation options.

## Evidence of Divergence
- Phase 2 conversation text differs between the two runs despite identical configuration and seed, e.g. the first two lines of the public transcript (`experiment_results_20251002_113622.json:7` vs `experiment_results_20251002_113844.json:7`). Even the "(initiated vote)" tag moves between participants in the voting confirmation lines (`experiment_results_20251002_113622.json:9` vs `experiment_results_20251002_113844.json:9`).
- Timestamps attached to ballot records and confirmation metadata change on each execution (`experiment_results_20251002_113622.json:183` and `experiment_results_20251002_113844.json:183`).

## Deterministic Controls Already in Place
- The experiment manager initializes a dedicated `SeedManager` per run and threads its RNG through all internal randomness (`core/experiment_manager.py:170`, `core/services/counterfactuals_service.py:153-193`, `core/phase1_manager.py:355`).
- Prompt scoping is seeded as well: the language manager is created with the same experiment seed so contextual headers, principle lists, and memory formatting stay bit-identical across runs (`main.py:104-116`, `utils/language_manager.py:224-255`, `utils/language_manager.py:681-713`).
- Income distributions, counterfactual tables, and speaking-order shuffles all defer to the experiment RNG, so numerical outcomes (earnings, class assignments) repeat faithfully.

## Sources of Non-Determinism
### 1. External LLM Calls (dominant culprit)
All participant statements, retry flows, voting prompts, and utility parsing are delegated to remote models via `Runner.run`, and no seed is supplied to those API calls.
- Participant discourse is generated by `Runner.run(participant.agent, …)` during Phase 2 (`core/phase2_manager.py:334-398`), so even with `temperature=0`, any provider-side sampling jitter or load-balancing can produce alternate wordings.
- Vote initiation and confirmation prompts are likewise round-tripped through the model (`core/services/voting_service.py:146-299`), which explains the flipped "initiated vote" label — whichever agent responded "1" first is tagged as the initiator in `conduct_public_confirmation` (`core/services/voting_service.py:253-299`).
- Utility agents and temperature capability checks fire their own probe completions (`experiment_agents/participant_agent.py:50-139`, `utils/dynamic_model_capabilities.py:311-344`), adding yet more remote calls whose responses are outside our seed control.

Because the OpenAI Agents SDK does not expose a `seed` parameter through `ModelSettings`, we currently have no way to request deterministic completions from these providers. As long as those APIs remain stochastic, transcript-level drift is unavoidable.

### 2. Time-Based Logging
Voting payloads capture `datetime.now()` for individual ballots and vote summaries, guaranteeing per-run differences even if the textual outputs matched (`core/two_stage_voting_manager.py:904-917`). The same applies to confirmation analytics recorded by the agent-centric logger (`utils/logging/agent_centric_logger.py:321`). These timestamps feed directly into the exported JSON (`experiment_results_20251002_113622.json:183`).

### 3. Run Metadata
Each experiment and discussion state is tagged with a fresh UUID (`core/experiment_manager.py:67`, `models/experiment_types.py:163`) and individual statements carry `datetime.now()` timestamps (`models/experiment_types.py:153`). These identifiers do not currently leak into prompts, but they do alter diagnostics, trace names, and any downstream analytics keyed by run ID.

## Impact
- Narrative drift: agent statements change in tone and phrasing, and vote-initiation attribution can flip, complicating regression comparisons.
- Log divergence: per-vote timestamps and UUIDs make raw JSON diffs noisy even when consensus outcomes agree.
- Downstream reproducibility: any ML evaluation or audit trail that depends on exact transcripts cannot rely solely on `seed` and `temperature` today.

## Recommendations
1. **Document the contract** – make it explicit in user-facing docs that external provider calls remain nondeterministic despite seed/temperature controls, and that exported timestamps will differ between runs.
2. **Introduce a deterministic mode** – add an opt-in adapter that records LLM responses the first time and replays them on subsequent runs (or swap to a local provider such as Ollama) when strict reproducibility is required.
3. **Explore provider seeding hooks** – if the Agents SDK exposes `extra_body`/`extra_args`, experiment with passing a `seed` parameter so that providers capable of deterministic decoding can honour it. Otherwise track the SDK issues for upstream support.
4. **Make timestamps optional** – gate `datetime.now()` writes behind a configurational flag or replace them with run-relative counters when reproducibility matters, so JSON comparisons stay clean.
5. **Add regression checks** – extend the existing reproducibility tests to assert that numeric outcomes stay stable while tolerating transcript drift, keeping us alerted if deterministic guarantees erode further.

With these mitigations, we can preserve the current fairness logic while signalling — and, where possible, shrinking — the gap between seeded randomness and end-to-end determinism.
