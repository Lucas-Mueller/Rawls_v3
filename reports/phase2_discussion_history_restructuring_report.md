# Phase 2 Discussion History Restructuring Report

Author: Codex CLI
Date: 2025-09-05

## Executive Summary

- Goal: During Phase 2, expose the ongoing discussion history only via the agent’s instruction (system) prompt, and always keep it up‑to‑date. Remove discussion history from the user/input prompt content.
- Current state: Discussion history is injected directly into several Phase 2 input prompts, while the instruction prompt does not reliably include it. This leads to duplicated context and inconsistent updates.
- Plan: Move discussion history into the instruction layer generated by `ParticipantAgent` and stop including it in the input prompts built by `DiscussionService`. Synchronize the latest history into each participant’s `ParticipantContext` before every LLM call in Phase 2.

---

## Current Implementation

### Data Model
- `models/experiment_types.py`
  - `GroupDiscussionState.public_history: str` accumulates formatted statements and voting events.
  - `GroupDiscussionState.add_statement(...)` appends statements to `public_history` (localized format when available).
  - `GroupDiscussionState.add_vote_result(...)` appends summary lines for voting to `public_history`.
  - `ParticipantContext` has no dedicated field for discussion history; it carries `memory`, `internal_reasoning`, and other context fields.

### Where Discussion History Is Built
- `GroupDiscussionState` is the canonical source of truth for the discussion transcript (`public_history`).
- `core/phase2_manager.py` advances `GroupDiscussionState` via:
  - `_process_participant_statement(...)` → calls `DiscussionService.manage_discussion_history_length(...)` then `discussion_state.add_statement(...)`.
  - `_attempt_end_of_round_voting(...)` → `VotingService` updates `discussion_state` via vote result paths.

### Where Discussion History Is Consumed in Prompts
- `core/services/discussion_service.py`
  - `build_discussion_prompt(...)` injects `discussion_state.public_history` into `prompts.phase2_discussion_prompt`.
  - `build_internal_reasoning_prompt(...)` injects `discussion_state.public_history` into `prompts.phase2_internal_reasoning`.
- `utils/language_manager.py`
  - `get_phase2_instructions(...)` returns `prompts.phase2_discussion_prompt` but explicitly passes `discussion_history=""` and `group_participants=""`, i.e., the Phase 2 instruction block does not contain the actual history.
  - `format_context_info(...)` builds the instruction/system prompt from pieces (memory section, internal reasoning section, experiment explanation, phase instructions, language instruction). There is no dedicated “Discussion History” section.

### How Instructions Are Produced
- `experiment_agents/participant_agent.py`
  - The agent is constructed with a dynamic `instructions` lambda → `_generate_dynamic_instructions(...)`.
  - That function calls `language_manager.format_context_info(...)`, feeding it:
    - Participant identity, balance, phase/round
    - A memory section (usually “full” display)
    - Phase instructions via `language_manager.get_phase2_instructions(round, max_rounds)`
    - Optional “internal reasoning section” from `context.internal_reasoning`
  - Because `get_phase2_instructions(...)` zeroes out `discussion_history`, the instruction prompt currently does not include the real discussion transcript.

### Summary of the Mismatch
- Input prompts include discussion history (via `DiscussionService`), while the instruction prompt does not.
- As a result, the LLM receives duplicated and potentially inconsistent context: a blank/boilerplate instruction plus a history‑heavy input prompt.
- This is the opposite of the target state (history only in instruction, always up‑to‑date).

---

## Target State

- The discussion transcript is shown only in the instruction/system prompt. The input prompt text is concise (e.g., “What is your statement for this round?”) and does not embed the transcript.
- The instruction is always up‑to‑date for each participant at the moment of each LLM call (internal reasoning, public statement, vote prompts where relevant).
- History is still trimmed per `Phase2Settings.public_history_max_length`, and the truncated version is what appears in the instruction.

---

## Design Overview (Proposed)

1. Add a new field to `ParticipantContext` to carry discussion history for instruction generation.
   - `discussion_history: str = ""` (non‑breaking default).

2. Synchronize the latest `GroupDiscussionState.public_history` into each participant’s `ParticipantContext.discussion_history` immediately before each LLM call in Phase 2.
   - Applies to internal reasoning, public statements, and vote prompts (if any input prompt needs context).

3. Update instruction generation to include a “Discussion History” section during Phase 2.
   - Extend `language_manager.format_context_info(...)` to accept an optional `discussion_history` and render a section when present.
   - Alternatively (lower surface area): keep `format_context_info` unchanged and instead compute Phase 2 instructions by calling a new helper (e.g., `language_manager.format_phase2_discussion_instructions(...)`) that outputs the Round header, group composition, and a transcript section.
   - In both approaches, the instructions must be generated from `context.discussion_history` and not from `DiscussionService` to keep layering clean.

4. Stop injecting discussion history into input prompts built by `DiscussionService`.
   - `build_discussion_prompt(...)` and `build_internal_reasoning_prompt(...)` should no longer include `{discussion_history}`.
   - Replace with short, task‑focused prompts.

5. Keep trimming logic exactly where it is (`DiscussionService.manage_discussion_history_length(...)`). The trimmed history is what gets synchronized into contexts.

## Detailed Change Plan

### A. Data Model
- File: `models/experiment_types.py`
  - Add `discussion_history: str = Field(default="", description="Phase 2 public discussion transcript for instruction context")` to `ParticipantContext`.
  - Backward compatibility: Default empty string ensures Phase 1 and existing code paths remain unaffected.

### B. Synchronization Points
- File: `core/phase2_manager.py`
  - In `_process_participant_statement(...)` BEFORE building prompts:
    - Set `context.discussion_history = discussion_state.public_history` (already trimmed at this point).
    - Also set `context.interaction_type = "internal_reasoning"` or `"statement"` as currently done, so instructions can adapt formatting if desired.
  - In `_attempt_end_of_round_voting(...)` before each `prompt_for_vote_initiation(...)` call:
    - Set `context.discussion_history = discussion_state.public_history` so the instruction includes the latest transcript when the agent decides whether to vote.
  - Optionally do the same at the start of each round loop for all contexts, to ensure each participant has a fresh copy.

### C. Instruction Generation
- File: `experiment_agents/participant_agent.py`
  - Update `_generate_dynamic_instructions(...)` for `ExperimentPhase.PHASE_2`:
    - Compute Phase 2 instructions using `context.round_number`, `experiment_config.phase2_rounds`, current group composition (names available in `Phase2Manager`), and `context.discussion_history`.
    - Two equivalent options:
      1) Extend `language_manager.get_phase2_instructions(round, max_rounds, discussion_history, group_participants)` to accept `discussion_history` and `group_participants`, and inside it compose a Phase 2 block that includes the transcript. Then pass its result into `format_context_info(...)` as `phase_instructions`.
      2) Keep `get_phase2_instructions` API as‑is and add a new `language_manager.format_phase2_discussion_instructions(...)` used only when `phase == PHASE_2`. Pass that formatted section instead of the current `get_phase2_instructions(...)` output.
    - Keep other instruction parts unchanged (memory section, internal reasoning section, language instruction).

### D. Input Prompt Builders
- File: `core/services/discussion_service.py`
  - `build_discussion_prompt(...)`:
    - Remove `{discussion_history}` from the prompt. Use a concise template (e.g., “GROUP DISCUSSION - Round X of Y. What is your statement to the group for this round?”), or introduce a new key like `prompts.phase2_discussion_short_prompt` that does not include history.
  - `build_internal_reasoning_prompt(...)`:
    - Remove `{discussion_history}` from the prompt. Keep the reflective questions only.
  - Keep `format_group_composition(...)` as‑is; decide whether group composition belongs in instructions (recommended) instead of the input prompt to avoid duplication. If kept, keep it brief.

### E. Translation and Templates
- Files: `translations/*_prompts.json`
  - Add new keys or adjust existing ones to avoid history in input prompts:
    - New: `prompts.phase2_discussion_short_prompt` (no `{discussion_history}` placeholder).
    - New: `prompts.phase2_internal_reasoning_short` (no `{discussion_history}` placeholder).
  - Add instruction‑layer formatting support for transcript:
    - New: `context_discussion_history_section_format`:
      - Example (EN):
        ```
        === DISCUSSION HISTORY ===
        {discussion_history}
        ==========================
        ```
    - Optionally a `context_group_composition_format` for rendering participant names in the instruction.
  - If minimizing translation churn: Keep existing keys, but drive transcript rendering through a new `language_manager.format_phase2_discussion_instructions(...)` that composes using existing building blocks and simple localized labels.

### F. Trimming & Limits
- Keep `DiscussionService.manage_discussion_history_length(...)` unchanged. Ensure synchronization happens AFTER trimming to avoid instruction bloat.
- Consider exposing `public_history_max_length` in the instruction rendering plan to warn about truncation via existing `system_messages.discussion.truncation_marker`.

### G. Logging & Persistence
- No changes needed for `AgentCentricLogger` or JSON schemas; discussion history remains in `Phase2Results.discussion_result.discussion_history`.
- Memory updates remain independent; moving transcript to instructions does not affect memory content.

## Validation Plan

1. Unit tests
   - Instruction contains transcript:
     - Arrange a `ParticipantContext` with `phase=PHASE_2` and a sample `discussion_history`.
     - Call `_generate_dynamic_instructions(...)` and assert that the output contains the transcript and the correct round header.
   - Input prompts are slim:
     - Call `DiscussionService.build_discussion_prompt(...)` and assert it does NOT contain “Discussion History”.
     - Call `build_internal_reasoning_prompt(...)` and assert it does NOT contain “Discussion History”.
   - Trimming reflects in instructions:
     - After calling `manage_discussion_history_length(...)`, set `context.discussion_history` and assert instructions include the truncated form with the truncation marker.

2. Integration test (single round)
   - Run a Phase 2 round with 2+ participants.
   - Verify via captured prompts (or logs) that:
     - Instructions for each participant contain the latest transcript specific to their call time.
     - Input prompt for statements does not embed the history.
     - After participant A speaks, participant B’s instructions include A’s statement before B’s turn.

3. Regression checks
   - Phase 1 prompts unchanged.
   - Phase 2 voting flow unaffected; if vote prompts need context, they rely on instructions with transcript.

## Risks and Mitigations

- Risk: Increased instruction size could push some models over token limits.
  - Mitigation: Keep `public_history_max_length` conservative; consider adaptive trimming (e.g., keep last N lines) if needed.

- Risk: Duplicate history if `DiscussionService` prompt changes are incomplete.
  - Mitigation: Add a unit test asserting input prompts do not contain “Discussion History”.

- Risk: Translation churn across three languages.
  - Mitigation: Start with English; add ES/ZH in a follow‑up commit. Provide English fallbacks if keys are missing.

- Risk: Coupling between `Phase2Manager` and `ParticipantAgent` through `ParticipantContext` field.
  - Mitigation: The field is generic, lives on the context, and has a default value for backward compatibility.

---

## Non‑Goals

- Changing how memory is updated or summarized.
- Changing voting algorithms or consensus validation.
- Altering logging schemas beyond what already exists.

## Recommended Path (Minimal Diff Option)

1) Add `discussion_history` to `ParticipantContext` and synchronize it from `GroupDiscussionState` immediately before each LLM call.

2) In `_generate_dynamic_instructions`, bypass `get_phase2_instructions(...)` for Phase 2 and instead compute a Phase 2 instruction section that includes:
   - Round header (X of Y)
   - Group composition (optional)
   - A transcript section using `context.discussion_history`
   - Use a new `language_manager.format_phase2_discussion_instructions(...)` to reduce changes elsewhere.

3) Switch `DiscussionService` input prompts to short, transcript‑free templates.

This approach confines most logic to `ParticipantContext`, `Phase2Manager`, and `ParticipantAgent` while keeping service boundaries and existing logging intact.
